# 업무보고서(report) family 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 경상북도경제진흥원의 「주요업무보고」를 DSL에서 한글이 여는 HWPX로 만들어 내는 `report` family를 더한다.

**Architecture:** 기존 4개 family와 같은 길을 쓴다 — `FamilySchema`에 값을 더하면 컴파일러가 채워야 할 자리 8곳을 가리키고, 작성기는 큐레이션한 참고 패키지(`templates/report/pkg/`)를 바탕으로 `Contents/section0.xml`만 다시 만든다. 반복되는 머리·박스는 `plan.ts`처럼 상수로 짜고, 고정된 조직도 표 하나만 `geometry/tNN.xml`을 복제한다.

**Tech Stack:** TypeScript · Next.js · zod 4 · vitest · `bin/rhwp` · `@resvg/resvg-js`

**Spec:** `docs/specs/2026-09-21-공문서-업무보고서-설계.md` (§5.3은 2026-09-22 실측으로 개정됨 — **그 개정판을 읽어라**)

## 분기점 (먼저 읽을 것)

이 계획은 **`feat/official-document` 위에서** 시작한다. `main`이 아니다.

스펙 §7은 "단계 2(공문)와 3(업무보고)은 서로 독립"이라고 했지만, 그것은 단계 4(kind·UI)가 따로 있을 때의 이야기였다. 실제로는 단계 4가 공문 작업에 흡수되어 `lib/kinds.ts`·`STAGE_FAMILY`·종류 선택 UI가 전부 `feat/official-document`에 있고 `main`에는 없다. `report` kind는 그 셋을 모두 쓴다.

따라서 **병합 순서는 2 → 3**이다. 공문 브랜치가 `main`에 들어가기 전에는 이 작업을 `main`에서 시작할 수 없다.

## 전역 제약

- 기존 4종(`notice`·`plan`·`press`·`official`)의 HWPX 출력과 다운로드 파일명은 **바이트 단위로 불변**이어야 한다.
- `lib/docmodel/**` 는 `lib/hwpx/**` 를 import 하지 않는다.
- 모든 family 테이블은 `Record<Family, …>` 를 유지한다. 항목 누락이 컴파일 오류여야 한다.
- **새 블록 종류를 추가하지 않는다**(스펙 §5.3). 기존 `coverTitle`·`tocLine`·`chapterBand`·`sectionChip`·`table`·`para`·`blank`·`pageBreak`로 짠다.
- 새 DB 열을 만들지 않는다. `projects.kind`가 유일한 예외였고 이미 있다(스펙 §5.4).
- 매핑 타입은 **속성 문법**으로 쓴다(메서드 문법은 `strictFunctionTypes` 반공변 검사를 빠져나간다).
- zod 4.6.5: 중첩 `.default({})`는 **값을 파싱하지 않고 그대로** 돌려준다. `.default()` 달린 필드를 `.optional()`로 감싸 빌려 오면 기본값이 끼어든다. 기본값이 필요하면 **리터럴을 다 적는다**.
- 모든 과제는 `./node_modules/.bin/vitest run && pnpm typecheck && pnpm lint && pnpm build` 통과 후 커밋한다.
- `pnpm golden`은 **게이트가 아니다** — 인자 `notice 6-1`을 받는 공고문 대조용 진단 스크립트이고 `render-diff exit 3`은 `main`에서도 같은 수치로 나온다. 얼어붙은 family의 게이트는 `tests/hwpx/golden{,.press,.official}.test.ts`다.
- `lib/agents/**` 를 고치면 dev 서버를 재시작해야 한다(러너가 `globalThis`에 상주).
- 커밋 메시지는 한국어 한 줄 제목 + 왜 그렇게 했는지. 끝에:
  `Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>`
  `Claude-Session: https://claude.ai/code/session_01Q8yRm2iqSzUiSA4vMmWFVs`

## 판정 (계획 단계에서 정한 것 — 뒤집으려면 근거를 적어라)

**판정 1 — 소제목 글머리 도형은 복제한다.**
글머리표 문자(`▣` 등)로 바꾸면 훨씬 싸지만, 23쪽짜리 문서의 모든 소제목에서 모양이 달라지고 이 문서는 원장·도지사에게 올라간다. `extract-geometry.ts`가 `tbl`만 덤프하므로 이 조각을 뜨는 것은 Task 4의 별도 단계다.
*틀렸을 때 비용*: Task 4가 한 단계 길어진다. 복제가 한글에서 깨지면 글머리표 문자로 내려온다(되돌리기 쉽다).

**판정 2 — 골든은 전사(全寫)하지 않는다.**
23쪽 39표를 다 옮기는 것은 그 자체로 하나의 과제이고, 얻는 것이 비례해서 늘지 않는다. 골든은 **표지 + 보고순서 + 간지Ⅰ + 일반현황(설립목적·연혁·조직도) + Ⅱ의 한 절**까지 만든다. 고정하는 항목은 `golden.test.ts`와 같은 종류다 — 경고 없음, 표 개수, 쪽수, `contentLoss 0`, 참고 텍스트 포함.
*틀렸을 때 비용*: 전사하지 않은 쪽에만 있는 서식 문제를 골든이 놓친다. Task 7의 한글 육안 확인이 그물이다.

**판정 3 — 목차 쪽번호는 1차에서 자리표시자다.**
점선 리더는 `tabPr 1`이 이미 준다(실측). 남는 것은 숫자뿐이고, 그것은 2패스(빌드 → `rhwp export-text` 쪽별 텍스트 → 절 위치 찾기 → 목차 갱신 → 재빌드)가 필요하다. 이 계획의 범위 밖이다.
*틀렸을 때 비용*: 담당자가 한글에서 목차 숫자를 손으로 고쳐야 한다. **Task 7에서 사용자에게 명시적으로 알린다** — 조용히 틀린 숫자를 내보내는 것이 가장 나쁘다. 자리표시자는 눈에 띄는 모양(`―`)으로 둔다.

**판정 4 — 조직도 내용은 템플릿에 굳힌다.**
`1본부 3실 1단 6팀 2지소`, 팀 이름, 인원 64명이 조직도 표 안에 있다. 이것을 메타로 빼면 `ReportMetaSchema`가 조직 전체를 들고 있어야 한다. `lib/org.ts`가 이미 조직을 알지만 조직도 **표의 칸 배치**까지 알지는 않는다.
1차에서는 `geometry/tNN.xml`을 그대로 복제한다(인원수 등 바뀌는 숫자만 셀 치환).
*틀렸을 때 비용*: 조직 개편 때 템플릿을 다시 뜬다. 연 1회 미만이고 그때 `lib/org.ts`도 함께 고쳐야 하므로 어차피 사람이 붙는다.
