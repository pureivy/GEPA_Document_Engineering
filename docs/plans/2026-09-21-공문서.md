# 공문서(official) 구현 계획

> **에이전트 작업자에게:** 이 계획은 `superpowers:subagent-driven-development`(권장) 또는 `superpowers:executing-plans`로 한 과제씩 실행한다. 단계는 체크박스(`- [ ]`)로 추적한다.

**목표:** 웹 화면에서 공문서를 만들어 HWPX로 내려받을 수 있게 한다 — 새 프로젝트에서 "공문"을 고르고, 에이전트가 본문을 쓰고, 편집기에서 고치고, 한글에서 열리는 파일을 받는 것까지.

**아키텍처:** 공문서는 고정 프레임 문서다. 참고 문서의 두문 표(t00)와 결문 표(t01)를 XML 그대로 복제해 `setCellText`로 값만 바꾸고, 그 사이에 본문 문단을 생성한다. 사업계획서 결재란(`lib/hwpx/writers/plan.ts:128-150`)이 이미 똑같이 동작하므로 새 기법이 아니다. 프로젝트에는 `kind` 를 두고 단계 목록을 거기서 파생해, 기존 4단계 파이프라인과 분리한다.

**기술 스택:** TypeScript, zod, Next 16.3.5 (App Router), drizzle/SQLite, vitest, Playwright, @rhwp/core

**스펙:** `docs/specs/2026-09-21-공문서-업무보고서-설계.md` (§5.2 공문서 · §5.4 kind·UI · §6 큐레이션)

**선행 완료:** family 레지스트리(`docs/plans/2026-09-21-family-레지스트리.md`, main 병합됨) · 템플릿 큐레이션(`d0f0f85`)

## 전역 제약

- 기존 3종(`notice`·`plan`·`press`)의 HWPX 출력과 다운로드 파일명은 **바이트 단위로 불변**이어야 한다. `pnpm golden` + `pnpm test` 가 판정한다.
- `lib/docmodel/**` 는 `lib/hwpx/**` 를 import 하지 않는다.
- 모든 family 테이블은 `Record<Family, …>` 를 유지한다. 항목 누락이 컴파일 오류여야 한다.
- **시행 일련번호를 생성하지 않는다.** 시행 칸은 `<처리과>-` 까지만 찍는다(사용자 확정 2026-09-21). `OfficialMeta` 에 `시행번호` 키를 두지 않는다 — 값을 담을 자리가 있으면 에이전트가 지어낸다.
- 모든 과제는 `pnpm test && pnpm typecheck && pnpm lint && pnpm golden` 통과 후 커밋한다.
- 커밋 메시지: 한글 한 줄 요약 + 필요 시 `- ` 불릿. 끝에 `Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>`.
- `lib/agents/**` 를 고치면 dev 서버를 재시작해야 한다(러너가 `globalThis` 에 상주).
- `pnpm golden` 은 `render-diff exit 3` 과 텍스트 줄 차이를 출력한다. **기존 잡음이다**(변경 전 트리에서 동일 재현 확인됨). `contentLoss 0` 과 `rhwp verify 판정: pass` 만 보면 된다.

import { OfficialMetaSchema, officialMetaProblems } from "../../lib/docmodel/schema";

const BASE = {

  수신자: ["경영지원팀장", "마케팅팀장"],

describe("OfficialMetaSchema", () => {

`lib/docmodel/schema.ts` 의 `PressMetaSchema` 정의 바로 뒤에 넣는다. `DocModelSchema` 는 아직 건드리지 않는다.

```ts
/**
 * 공문서 — 행정안전부 「행정업무의 운영 및 혁신에 관한 규정」 시행규칙 별지 제1호 일반기안문.
 * 가변부는 수신 / 제목 / 본문 / 붙임 네 가지뿐이고 나머지는 프레임과 조직 데이터다.
 *
 * 시행 일련번호는 이 스키마에 없다. 전자결재 시스템이 기안 후에 채번하므로 우리는 만들지 않는다
 * (시행 칸은 `<처리과>-` 까지만 찍는다). 값을 담을 자리를 두면 에이전트가 지어낸다.
 */
export const OfficialMetaSchema = z
  .object({
    수신유형: z.enum(["내부결재", "수신자", "수신자참조"]),
    /** 수신유형=수신자 일 때의 수신자 — 예: "경영기획실장(경영지원팀장)" */
    수신: z.string().optional(),
    /** 수신유형=수신자참조 일 때의 수신자 목록 */
    수신자: z.array(z.string()).optional(),
    경유: z.string().default(""),
    제목: z.string().min(1),
    /** 결문 발신명의. 비우면 lib/org.ts 가 부서에서 추론한다 */
    발신명의: z.string().default(""),
    /** 기안 부서(팀). 시행 칸에 `<처리과>-` 로 찍힌다 */
    처리과: z.string().min(1),
    /** 시행일. 시행 전에는 빈 문자열 */
    시행일: z.string().default(""),
    공개구분: z.enum(["공개", "부분공개", "비공개"]).default("공개"),
    /** 결재란 직위. 비우면 lib/org.ts 의 approvalLineFor(처리과) */
    결재라인: z.array(z.string()).default([]),
    협조자: z.array(z.string()).default([]),
    연락처: z
      .object({
        우편번호: z.string().default(""),
        주소: z.string().default(""),
        홈페이지: z.string().default("https://gepa.kr"),
        전화: z.string().default(""),
        전송: z.string().default(""),
        이메일: z.string().default(""),
      })
      // zod 4 에서 객체의 .default(v) 는 v 를 **파싱하지 않고 그대로 돌려준다**(실측 확인).
      // 따라서 .default({}) 는 타입도 안 맞고, 통과하더라도 런타임에 연락처가 빈 객체가 된다.
      // 안쪽 기본값과 같은 전체 리터럴을 적는다. .prefault() 는 쓰지 말 것 —
      // unwrapSchema(frontmatter.ts:116)가 못 푸는 클래스라 연락처 안의 미지 키 검사가 죽는다.
      .default({ 우편번호: "", 주소: "", 홈페이지: "https://gepa.kr", 전화: "", 전송: "", 이메일: "" }),
    붙임: z.array(z.string()).default([]),
  });
export type OfficialMeta = z.infer<typeof OfficialMetaSchema>;

/**
 * 수신유형과 수신·수신자의 정합성 검사. 사람이 읽는 문제 목록을 돌려준다(빈 배열이면 정상).
 *
 * 이것을 zod `.superRefine()` 으로 넣지 않는 이유: superRefine 으로 감싸도 여전히 ZodObject 라
 * unwrapSchema(frontmatter.ts:116)·collectUnknownKeys 는 멀쩡히 동작한다(zod 4.6.5 실측) — 그건
 * 문제가 아니다. 진짜 이유는 **판정의 성격**이다. superRefine 은 안 맞으면 파싱 자체를 실패시키는데,
 * 이 호출처(작성기의 ctx.warnings, 검토관)는 문서를 **경고와 함께라도 만들어 내야** 한다 — 수신유형과
 * 수신·수신자가 안 맞아도 문서는 나오고, 사람이 읽는 문제 목록만 곁들인다. 스키마 파싱을 막으면
 * 그 자리에서 작성이 멈춘다.
 */
export function officialMetaProblems(m: OfficialMeta): string[] {
  const out: string[] = [];
  if (m.수신유형 === "수신자" && !m.수신?.trim()) out.push("수신유형이 '수신자'면 수신을 적어야 합니다");

 * `review` 는 어느 kind 의 단계 목록에도 없다 — 문서 단계에 덧붙는 별도 실행이다.
 */
import type { Stage } from "./contracts";

export type ProjectKind = "program" | "official";
export const PROJECT_KINDS: ProjectKind[] = ["program", "official"];
export const KIND_LABEL: Record<ProjectKind, string> = { program: "사업", official: "공문" };
export const KIND_STAGES: Record<ProjectKind, Stage[]> = {
  program: ["research", "plan", "notice", "press"],
  official: ["official"],
};
export function stagesOf(kind: ProjectKind): Stage[] {
  return KIND_STAGES[kind];
}
export function isProjectKind(v: unknown): v is ProjectKind {
  return typeof v === "string" && (PROJECT_KINDS as string[]).includes(v);
}
```

### Task 6: 골든과 마감 검증

**파일**
- 생성: `templates/official/golden/<name>.dsl.md` · `templates/official/reference.text.txt`
- 수정: `scripts/golden.ts:56` (family 별 기대 문자열)
- 테스트: `tests/hwpx/golden.official.test.ts` (신규)

- [ ] **단계 1: 참고 문서의 텍스트를 뽑는다**

`export-text` 는 입력 파일 하나만 받고 **폴더**로 내보낸다(페이지별 TXT). 컨트롤러가 실행해 확인한 사용법:
```bash
./bin/rhwp export-text templates/official/reference.hwpx -o /tmp/official-text
cat /tmp/official-text/*.txt > templates/official/reference.text.txt
```
공문서는 1쪽이므로 파일도 하나다.

**⚠ 추출 순서가 문서에 보이는 순서와 다르다 — 컨트롤러가 실측한 사실이다.**
`export-text` 는 **표 밖 문단을 먼저** 쓰고 **표 안 내용을 뒤에** 붙인다. 실제 출력:
```
경영평가 상시대응체계 구축 및 …     ← 본문이 먼저
1. 작성대상: …
붙임 … 끝.
(재)경상북도경제진흥원              ← 두문이 나중
수 신
```
따라서 **줄 순서로 비교하는 골든은 반드시 실패한다.** 공문서 골든은 순서가 아니라
**포함 여부와 값**으로 비교한다 — 두문의 수신·제목, 본문 각 항목, 붙임·`끝.` 줄,
결문의 발신명의·결재란 직위·시행 칸(`<처리과>-` 이고 숫자가 없을 것)·연락처가
각각 들어 있는지 확인하는 형태로 짠다. `tests/hwpx/golden.press.test.ts` 가 줄 순서에
의존한다면 그 구조를 그대로 베끼지 말고, 이 제약에 맞게 고쳐 쓴다.
