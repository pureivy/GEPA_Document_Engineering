# 공문서·업무보고서 도입 설계

**작성일** 2026-09-21 · **상태** 검토 대기(방향은 2026-09-21 승인) · **후속** 구현 계획

## 1. 배경과 목표

현재 시스템은 **조사 → 사업계획서 → 공고문 → 보도자료** 네 단계가 한 프로젝트 안에서 이어지는 구조다.
진흥원이 실제로 생산하는 문서에는 이 연쇄에 속하지 않는 두 종류가 더 있다.

- **발송 공문서** — 행정안전부 「행정업무의 운영 및 혁신에 관한 규정」 시행규칙 별지 제1호 일반기안문.
- **업무보고서** — 기관 주요업무보고. 표지·보고순서·간지를 갖춘 독립 서식.

두 문서는 **기존 파이프라인과도, 기존 서식 체계와도 분리**한다. 각각 단독으로 실행되고, 자체 템플릿·작성기·에이전트를 갖는다.

**목표**: 새 문서 유형 2종을 추가하되, 실행·버전·실시간 타이핑·편집기·렌더·내보내기·검토관 배관은 기존 것을 그대로 재사용한다.

## 2. 범위

### 포함
- DocModel family `official`(공문서), `report`(업무보고서) 신설
- `templates/official/`, `templates/report/` 큐레이션
- family 축 레지스트리화(기존 3종 동작 불변 리팩터링)
- 프로젝트 `kind` 도입과 단계 목록 파생
- 에이전트 페르소나·디자인 스킬·프롬프트·모델 배정

### 제외
- 전자결재 시스템(새올) 연동. 시행 일련번호·접수번호는 채번하지 않는다 — 시행 칸은 `<처리과>-` 까지만 찍는다(§5.2).
- 업무보고서 목차의 실제 쪽번호 계산(§10 후속 과제).
- 기존 4단계 파이프라인의 동작 변경.

## 4. 현행 구조 조사 결과

1. **`family`는 DocModel 안에만 산다.** 파일 경로·DB 행·URL·에이전트 작업폴더·프롬프트·모델·한도는 전부 `stage` 문자열로 키가 잡힌다. 두 축을 잇는 다리는 `lib/contracts.ts:10` `STAGE_FAMILY` 하나이고, 읽는 곳은 `components/stage/StageRunner.tsx:41` 한 군데다.
2. **`stage`에는 DB 제약이 없다.** `lib/db/migrations/0000_init.sql`이 `stage text NOT NULL`(CHECK 없음)이고, `STAGE_VALUES`(`lib/db/schema.ts:5`)는 TS 타입일 뿐이다. 디스크도 `data/projects/<id>/<stage>/`를 필요할 때 mkdir 한다. **새 문서 유형 자체는 마이그레이션이 없다.**
3. **단계 게이팅이 원래 없다.** `PIPELINE`(`lib/stages/runIntegration.ts:43`)의 유일한 소비자는 `nextStage`→`chainNext`이고 `autoChain`일 때만 돈다. 실행 라우트는 선행 단계를 확인하지 않는다. **`review`가 이미 `PIPELINE` 밖 단계로 존재한다** — 비연쇄 단계의 선례.
4. **`BlockSchema`·`ParaRoleSchema`는 이미 family 비종속 평면 열거형**이다(`lib/docmodel/schema.ts:108-161`, `:31`). 기존 블록·역할을 재사용하면 스키마 변경이 없다. 새 블록 종류 추가는 파서 + 작성기 3 + 직렬화기 3 + 편집기 노드로 번진다.
5. **조용한 fall-through가 최대 위험이다.** (2026-09-21 실측으로 보정 — 초안의 "15곳"은 과장이었다.
   `FamilySchema` 에 네 번째 값을 임시로 넣고 `pnpm typecheck` 를 돌려 확인했다.)

   **컴파일러가 잡아 주는 곳** — 새 family 추가 시 오류로 알려 준다:
   `lib/hwpx/template.ts:31`(TEMPLATE_FAMILY) · `lib/docmodel/dsl/frontmatter.ts:186,196,231,250,253,254`(META_SCHEMAS·fallbackMeta) ·
   `lib/docmodel/dsl/expanders/index.ts:13`(망라 switch) · `lib/docmodel/dsl/index.ts:157` ·
   **`components/editor/MetaSheet.tsx:16,19,26`** · **`components/editor/nodes/table.ts:21`**
   (뒤의 둘은 초안에서 놓쳤던 곳이다 — 편집기 UI도 family 테이블을 갖고 있으므로 새 family는 여기에도 항목이 필요하다.)

   **조용히 오작동하는 곳** (2026-09-21 리뷰로 갱신 — 아래 실측 방법의 한계상 이 목록이 전부라는 보장은 없다):
   - `lib/docmodel/indent.ts:20` — 삼항 연쇄가 `PRESS`로 끝나 보도자료 사다리를 씀
   - `lib/hwpx/build.ts` 작성기 선택 — `else` 가 `writePress` 로 흘러 **잘못된 문서가 검증을 통과**함(실측에서 이 파일만 오류가 안 났다)
   - `lib/stages/runIntegration.ts:96` `isDocStage` — 스트리밍·저장·내보내기가 통째로 조용히 무시됨
   - `app/api/projects/[id]/stages/[stage]/download/route.ts:21` — 다운로드 파일명을 만드는 삼항 연쇄가 `제목 + "_보도자료"`로 끝나, 네 번째 family(공문서)도 `제목`을 갖고 있어 컴파일은 그대로 통과한 채 파일명만 틀리게 나온다. family 레지스트리 리팩터(§5.1)에서 `exportBaseName`으로 고쳤다.

   **실측 방법의 한계**: 위 조사는 `FamilySchema`에 네 번째 값을 임시로 넣고 `pnpm typecheck`가 오류를 내는지만 봤다. 이 방법은 `Record<Family, …>` 항목 누락은 찾아내지만, `download/route.ts:21`처럼 마지막 분기가 이미 다른 family에도 통하는 필드(`제목`)를 쓰는 **삼항 연쇄**는 그대로 컴파일되므로 걸러내지 못한다. "실제로는 셋뿐이다"는 이 사각지대를 감안하지 않은 과장이었다 — 타입체크 실험이 못 잡는 fall-through가 최소 하나 더 있었다.

   직렬화기(`toMarkdown.ts:121`·`toText.ts:88`)와 `parser.ts` 분기 등 나머지는 블록 종류(`case "noticeHeader":`)로
   보호되어 있어 새 family가 도달하지 않는다. 초안은 이것을 위험으로 잘못 셌다.

   추가로 발견: `lib/docmodel/govLint.ts:93` 의 붙임·`끝.` 검사가 `plan|notice` 로 한정되어 **공문서가 검사에서 빠진다.**
   붙임·끝 은 시행규칙 제4조의 법정 요구사항이라 반드시 켜야 한다.
6. **템플릿 런타임 필수 산출물은 셋뿐**이다: `pkg/`, `style-map.json`, (plan만) `geometry/`.
   `pkg/`는 `scripts/curate-template.ts <family>`(argv 구동, family 하드코딩 없음)가 만든다.
   **`style-map.json`은 생성기가 없는 수작업**이고 역할 이름이 family마다 거의 겹치지 않는다(공고문 45·계획서 19·보도자료 17). 여기가 실제 공수다.
7. **`masterpage0.xml`은 자동으로 보존된다.** `curate-template.ts:58`이 전체 zip 엔트리를 순회하고(rhwp 마커만 제외), `lib/hwpx/template.ts:65`가 `header.xml`·`section0.xml` 외 전부를 `files`에 그대로 싣는다. 별도 작업이 필요 없다.
8. **4단계를 열거하는 지점** (전부 수정 대상):
   `lib/contracts.ts:7-10` · `lib/agents/runner.ts:9-13` · `app/projects/[id]/[stage]/page.tsx:8`(유일한 문서 URL, 모르는 단계는 404) · `components/pipeline/PipelineBar.tsx:18-24` · `StageRunner.tsx:398,412,450` · `ProjectOverview.tsx:26,29,57` · `lib/client/format.ts:35` · `lib/agents/limits.ts:24,33,57` · `lib/stages/runIntegration.ts:43-46,96,209`

## 5. 설계

### 5.1 family 레지스트리 (선행 리팩터링)

§4.5의 조용한 fall-through를 구조적으로 제거한다. 새 파일 `lib/docmodel/families/index.ts`:

```ts
export interface FamilyDef {
  id: Family;
  label: string;                                   // "공문서"
  metaSchema: z.ZodTypeAny;                        // frontmatter.ts META_SCHEMAS
  fallbackMeta: () => DocModel["meta"];            // frontmatter.ts:231
  context: (meta: DocModel["meta"]) => FamilyContext;  // dsl/expanders/index.ts:14
  templateDir: string;                             // hwpx/template.ts:31
  write: (ctx: WriterContext, doc: DocModel) => XmlNode[];  // hwpx/build.ts:50-52
  indentLadder: Record<Glyph, number>;             // docmodel/indent.ts:20
  docTitle: (doc: DocModel) => string;             // hwpx/build.ts:31-32
  exportBaseName: (doc: DocModel) => string;       // toDsl.ts:237
  headerLines?: { markdown(meta): string[]; text(meta): string[] };  // toMarkdown:121 / toText:88
  allowsSectionBar: boolean;                       // parser.ts:515
}

export const FAMILIES: Record<Family, FamilyDef> = { … };
```

`Record<Family, FamilyDef>` 이므로 **새 family에서 항목을 빠뜨리면 컴파일이 실패한다.**
24개 분기가 테이블 조회로 바뀌고, 기존 3종의 동작은 바뀌지 않는다. 골든 테스트와 기존 vitest가 안전망이다.

`FamilyStyle`(`lib/hwpx/writers/common.ts:17`)은 이미 `indentFamily`·`ladder`를 담은 데이터 객체이므로 그대로 둔다.

### 5.2 공문서 family `official`

**메타** (`OfficialMetaSchema`):

|---|---|---|

| `붙임` | string[] | `[]` |

**블록**: `officialHeader`(무필드), `officialFooter`(무필드) 2종만 추가한다.
`noticeHeader`·`pressHeader`와 같은 **합성 블록**(grammar 규칙 13)이라 작성자가 쓰지 않고 작성기가 메타에서 펼친다.
본문은 기존 `para`·`table` 어휘를 그대로 쓴다. 새 `ParaRole`은 추가하지 않는다.

**시행·접수 칸 규칙** (사용자 확정 2026-09-21): **일련번호는 우리가 만들지 않는다.**
시행 칸에는 **`<처리과>-` 까지만** 찍는다 — 예: `시행  마케팅팀-  (  )`.
번호와 시행일, 접수 칸은 모두 비운 채로 둔다. 기안 후 전자결재 시스템이 채번하며 채워 넣는다.

샘플에 `마케팅팀-2969`, `전략기획팀-485` 처럼 번호가 보이는 것은 **시행이 끝난 뒤의 문서**이기 때문이고,
우리가 생산하는 것은 그 이전 단계인 기안문이다. 따라서 `시행번호` 메타 키는 두지 않는다
(값을 담을 곳이 있으면 에이전트가 지어낼 여지가 생긴다).

**재사용**: `govLint`(날짜·쌍점·물결표·시간·금액·항목 위계·붙임/끝), `govNormalize`(저장 시 자동 정규화),
`format.ts`(`koreanAmount`·`govDate`), `org.ts`(결재라인·책임자·부서 정식명칭).

**DSL 예시**

```
---
family: official
수신유형: 수신자참조
수신자: [경영지원팀장, ESG·기업지원팀장, 마케팅팀장, 일자리종합지원팀장]
제목: 경영평가 대응을 위한 2026년 사업 추진 현황 제출 요청
발신명의: 경영기획실장
처리과: 전략기획팀
공개구분: 공개
붙임: ["(양식) 2026년 사업 추진 현황_팀명 1부."]
---
경영평가 상시대응체계 구축 및 원활한 사업 관리를 위해 2026년 사업 추진 현황을 매월 점검하고자 하오니 각 팀에서는 다음과 같이 자료를 제출하여 주시기 바랍니다.
1. 작성대상: 2026년 각 팀에서 운영하고 있는 전체 사업
2. 작성기준: 전월 말일 기준 사업별 예산 집행액 및 지원 현황
3. 제출방법: 대내 공문 발송
4. 제출기한: 매월 5일까지   ※ 7월 현황 제출 기한: 2026. 8. 10.(월) 14:00까지
5. 문 의 처: 전략기획팀 권하경(내선번호527)
```

붙임·`끝.` 줄은 `붙임` 메타에서 작성기가 생성하고, `govLint`가 표기를 검사한다.

### 5.3 업무보고서 family `report`

**메타** (`ReportMetaSchema`): `제목`, `보고일`, `보고대상`, `부서`, `대상기간`, `목차표시`(bool, 기본 true).

**블록**: 기존 `coverTitle`·`tocLine`·`chapterBand`·`sectionChip`·`table`·`para`를 재사용한다.
간지 쪽은 `chapterBand` + `pageBreak` 조합으로 표현한다. **새 블록 종류를 추가하지 않는다.**

**목차 쪽번호**는 1차에서 자리표시자로 둔다(§10).

**사다리·스타일**은 자체 `templates/report/style-map.json`으로 정의한다.
참고 파일도 `ㅇ`·`-`를 쓰지만 단계 구성과 들여쓰기 폭이 사업계획서와 다르므로, `plan`의 사다리를 재사용하지 않고 별도로 정의한다.

### 5.4 프로젝트 `kind`와 단계 파생

```ts
// lib/kinds.ts (신규)
export type ProjectKind = "program" | "official" | "report";
export const KIND_STAGES: Record<ProjectKind, Stage[]> = {
  program:  ["research", "plan", "notice", "press"],
  official: ["official"],
  report:   ["report"],
};
export function stagesOf(kind: ProjectKind): Stage[] { return KIND_STAGES[kind]; }
```

- `projects.kind` 컬럼 추가 — **이번 작업의 유일한 마이그레이션**. 기존 행은 `"program"` 기본값.
- §4.8의 각 지점에서 전역 `STAGES`를 `stagesOf(project.kind)`로 교체한다.
- `app/projects/[id]/[stage]/page.tsx:8`의 검증도 `stagesOf(kind)` 기준으로 바꾼다.
- **`STAGE_FAMILY`(`lib/contracts.ts:10`)에 `official: "official"`, `report: "report"` 를 추가한다.**
  이 한 줄이 stage 축과 family 축을 잇는 유일한 다리이므로 빠뜨리면 편집기 패널이 조용히 렌더되지 않는다(`StageRunner.tsx:501`).
- **흩어진 단계 목록 4개를 일원화한다.** 현재 `lib/contracts.ts:7`·`lib/agents/runner.ts:9`·`lib/db/schema.ts:5`·`lib/stages/runIntegration.ts:43`이
  서로 다른 값을 갖고 있다(`review`가 일부에만 있음). `lib/contracts.ts`를 **유일한 `Stage` 정의처**(`review` 포함)로 삼고 나머지는 이를 import 한다.
  `PIPELINE`은 `program` kind의 연쇄 정의로만 남긴다.
- `runIntegration.ts:96` `isDocStage`는 `STAGE_FAMILY[stage] !== undefined` 로 바꿔 새 단계가 조용히 누락되지 않게 한다.
- `PIPELINE`은 `program`에만 적용된다(`official`·`report`는 단일 단계이므로 자동연쇄가 돌지 않는다).
- 새 프로젝트 화면에서 kind를 선택하고, kind별로 다른 입력 폼을 보여준다.
  `official`은 수신·제목·부서, `report`는 제목·대상기간·부서를 받는다.
  이 값들은 **DB 컬럼이 아니라 프롬프트로 전달**되고, 에이전트가 front-matter에 써 넣는다 —
  지금의 주제·지역·주관기관·연락처와 같은 방식이다(`projects` 테이블은 그대로 둔다).

UI 명칭은 "프로젝트" 대신 kind에 맞춰 표기한다(`program`=사업, `official`=공문, `report`=보고서).

### 5.5 에이전트·스킬·프롬프트

기존 6칸 레시피를 그대로 따른다.

| 슬롯 | 공문서 | 업무보고서 |
|---|---|---|
| 템플릿 | `templates/official/` | `templates/report/` |
| 확장기 | `lib/docmodel/dsl/expanders/official.ts` | `.../report.ts` |
| 작성기 | `lib/hwpx/writers/official.ts` | `.../report.ts` |
| 고정문구 | 없음 | 없음 |
| 페르소나 | `agent/.claude/agents/official-writer.md` | `.../report-writer.md` |
| 디자인 스킬 | `agent/.claude/skills/gepa-official-design/` | `.../gepa-report-design/` |

- `scripts/sync-agent-skills.ts:6-12`에 두 쌍을 추가한다.
- `lib/agents/prompts/`에 두 단계의 시스템 프롬프트를 추가한다.

**`lib/agents/limits.ts`의 세 테이블을 확장한다** (전부 `Record<Stage,…>`라 누락은 컴파일 오류가 된다).

| 단계 | 모델 | 도구 | 한도 |
|---|---|---|---|
| `official` | `sonnet` | `["Read","Write"]` — 공고문·보도자료와 동일 | maxTurns 20 / 15분 |
| `report` | `opus` | `["WebSearch","WebFetch","Read","Write","Edit","Glob","Grep","Task"]` — 조사 단계와 동일 | maxTurns 45 / 35분 |

**`report`에 조사 도구를 주는 이유**: 주요업무보고는 이 시스템에서 가장 수치가 많은 문서다
(세입·세출예산, 사업별 실적, 조직·인원). `program` kind는 `research` 단계에서 내부 위키(`--add-dir`)와
공공데이터 MCP로 근거를 모으지만, `report`는 단일 단계이므로 **그 단계 안에서 직접 조사해야 한다.**
전년도 계획안·예산·실적이 들어 있는 내부 위키가 가장 중요한 자료원이다.
`official`은 사람이 사실을 이미 알고 있는 사무 문서이므로 조사 도구를 주지 않는다.

**검토관**: `reviewer.md`는 `DocModel`을 받으므로 골격 검사 로직 자체는 그대로 쓸 수 있다. 다만 두 가지가 필요하다.
- `app/api/projects/[id]/stages/[stage]/run/route.ts:21`의 `reviewTarget` enum에 `official`·`report`를 추가한다.
- `reviewer.md`의 점검 항목이 기존 세 family를 이름으로 지목하는 부분이 있는지 확인하고, 새 family의 검사 기준을 추가한다.
  공문서는 **시행 칸에 일련번호가 찍혀 있으면 오류**(§9), 붙임·`끝.` 표기, 수신유형과 수신자 필드의 정합성을 본다.

## 6. 템플릿 큐레이션 절차

두 family 모두 동일하다. `curate-template.ts`·`extract-style-map.ts`는 argv 구동이라 코드 변경이 없다.

1. 참고 파일을 `templates/<family>/` 에 둔다(git 제외).
   - 공문서: 한글이 저장한 `.hwpx` 이므로 `reference.hwpx` 로 두고 **`--from-hwpx`** 를 쓴다(변환 생략).
   - 업무보고서: `.hwp` 이므로 `reference.hwp` 로 두고 rhwp 변환을 거친다.
2. `pnpm exec tsx scripts/curate-template.ts <family> [--from-hwpx]` — 변환·검증·`pkg/` 생성.
3. `pnpm exec tsx scripts/extract-geometry.ts <family>` — **최상위 표 전부를 `geometry/tNN.xml` + `index.json`으로 자동 덤프**한다.
   공문서의 두문·결문 표는 기하가 고정이므로 이 XML을 작성기가 복제하는 편이 상수 하드코딩(보도자료 방식)보다 안전하다.
   `COVER_ALIASES`(`extract-geometry.ts:28`)는 표가 아닌 문단에 이름을 붙이는 선택 기능이고 `?? {}`로 처리되므로
   새 family에서 건드릴 필요가 없다.
4. `pnpm exec tsx scripts/extract-style-map.ts <family>` — `catalog.json` 생성(개발 참고용).
5. **`style-map.json`을 손으로 작성한다.** 역할 이름 → `{paraPr, charPr}` 매핑. 가장 큰 공수.
6. `package.json` `setup:templates`와 `scripts/sync-agent-skills.ts:6-12`에 항목을 추가한다.

## 8. 검증 계획

family마다 동일하게 적용한다.

- **골든 DSL** — `templates/<family>/golden/<name>.dsl.md` + `reference.text.txt`(수동 `rhwp export-text`).
  `scripts/golden.ts`의 공고문 전용 `--expect-contains`(`:56`)를 family별 인자로 일반화한다.
- **`@rhwp/core` 검증** — load + `exportHwpxWithReport().contentLoss == 0` + 쪽수 + SVG 렌더 + zip 레이아웃.
- **`rhwp verify` / `render-diff`**.
- **한글에서 직접 열기 1회** — ADR 0004대로 rhwp 검증은 필요조건일 뿐이다(rhwp는 관대하고 한글은 엄격).
  새 합성 블록(`officialHeader`·`officialFooter`)은 반드시 한글에서 한 번 연다.
- **단위 테스트** — `tests/docmodel`에 두 family의 front-matter 파싱·라운드트립, `tests/hwpx`에 작성기 테스트.
- **회귀** — 단계 1 리팩터링 후 `pnpm test && pnpm typecheck && pnpm lint && pnpm golden`이 모두 통과해야 한다.

## 9. 위험과 완화

| 위험 | 영향 | 완화 |
|---|---|---|
| 새 family가 기존 분기에서 조용히 오작동 | 잘못된 문서가 에러 없이 생성 | 단계 1 레지스트리를 **단계 2보다 먼저** 한다. `Record<Family,…>`가 누락을 컴파일 오류로 만든다 |
| `style-map.json` 수작업 분량 | 일정 지연 | 공문서는 프레임이 고정이라 역할 수가 적다. 업무보고서를 먼저 착수하지 않는다 |

## 10. 미해결 과제

- **업무보고서 목차 쪽번호** — DSL 작성 시점에 쪽수를 알 수 없다. `lib/stages/service.ts`의 `renderManifest`가 이미 쪽수를 주므로 2패스 빌드(1차 렌더 → 쪽수 수집 → 목차 갱신 → 재빌드)로 풀 수 있다. 1차 구현에서는 자리표시자로 두고 별도 과제로 뺀다.
- **업무보고서 조직도 도형** — 참고 파일은 도형으로 그려져 있다. 표로 대체할지 도형을 복제할지는 큐레이션 단계에서 `geometry/` 추출 결과를 보고 정한다.
- **결재란의 `★` 표시** — 샘플의 `★과장`이 기안자 표시인지 전결 표시인지는 큐레이션에서 원본 셀 속성을 보고 확정한다.
- **전자결재 연동** — 현재 범위 밖. 향후 시행번호 역채움이 필요하면 별도 설계한다.
